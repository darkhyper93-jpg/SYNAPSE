# Seguridad de un futuro leaderboard global para SYNAPSE (estado a octubre de 2026)

Contexto: hoy SYNAPSE es 100 % cliente (Capacitor 8 + Android WebView + PWA), sin backend ni cuentas. La puntuación se calcula en el dispositivo. El modo "Daily" usa 7 puzzles con una semilla derivada de la fecha, iguales para todos. Estas notas cubren qué cambia en seguridad si se añade un leaderboard (por ejemplo, para el Daily).

Nota sobre las fuentes: desde este entorno no se pudo acceder a firebase.google.com ni a supabase.com (el proxy de salida rechazó la conexión). La documentación de Supabase se leyó completa a través de la herramienta oficial de búsqueda de documentación de Supabase (MCP), con las URLs canónicas de supabase.com. La de Firebase solo se pudo ver en fragmentos de buscador, así que las afirmaciones sobre Firebase están marcadas como tales.

## Pregunta 1: ¿Qué puntos de un checklist genérico de seguridad "antes del lanzamiento" pasan a importar cuando existe un leaderboard o backend?

### Conclusión
Sin backend, casi todo el checklist (claves de API, RLS, autenticación, cookies, hashing de contraseñas, rate limiting, consultas parametrizadas, minimizar los datos devueltos) no aplica, porque no hay servidor ni datos compartidos. En cuanto existe un leaderboard, todos esos puntos pasan a ser relevantes. Aun así, con un BaaS (Supabase o Firebase) y autenticación anónima o de Play Games, varios los gestiona el proveedor: hashing de contraseñas, gestión de sesiones y, en gran parte, la parametrización de consultas. El trabajo propio se concentra en cuatro cosas: (a) políticas de acceso (RLS o Security Rules), (b) restricciones a nivel de campo, (c) validar y verificar la puntuación en el servidor y (d) limitar el abuso (rate limit, attestation, una entrada por usuario y día).

### Hallazgos citados
- **Claves de API / clave pública de la BD.** En Supabase, la clave publishable (`sb_publishable_...`) es "Safe to expose online: web page, mobile or desktop app... source code". En cambio, las secret keys (`sb_secret_...`) "provide *full access* to your project's data, bypassing Row Level Security" y solo deben usarse en backend. — [Supabase: Understanding API keys](https://supabase.com/docs/guides/getting-started/api-keys)
- Supabase indica que las claves publishable "are not intended to protect from... Static or dynamic code analysis and reverse engineering... Use of the Network inspector in the browser". Añade que el acceso a los datos lo protege Postgres mediante los roles `anon`/`authenticated`, y que hay que tener "enabled Row Level Security on all tables". — [Supabase: Understanding API keys](https://supabase.com/docs/guides/getting-started/api-keys)
- Las claves legacy `anon` y `service_role` "keep working until the end of 2026". Las secret keys nuevas "return HTTP 401 if used in a browser (matched on the User-Agent header)" y permiten tener una clave por servicio, para rotarlas por separado. — [Supabase: Migrating to publishable and secret API keys](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys)
- Lista de "Do not" de Supabase para las secret keys: no ponerlas en páginas web, código fuente ni ejecutables móviles; "Never use in a browser, even on localhost"; no pasarlas en URLs ni en query params. — [Supabase: Understanding API keys](https://supabase.com/docs/guides/getting-started/api-keys)
- **RLS.** "RLS *must* always be enabled on any tables stored in an exposed schema. By default, this is the public schema." Además, si la tabla se crea en SQL crudo, "remember to enable RLS yourself and grant only the permissions each Postgres role needs". — [Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- Sin RLS: "Tables that do not have RLS enabled with reasonable policies allow any client to access and modify their data." — [Supabase: Production Checklist](https://supabase.com/docs/guides/deployment/going-into-prod)
- **Las vistas se saltan la RLS por defecto.** "Views bypass RLS by default because they are usually created with the postgres user". La solución en Postgres 15+ es `security_invoker = true`. Esto importa si se crea una vista pública del ranking. — [Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **Manipulación de campos / mass assignment.** OWASP API Security Top 10 2023 incluye la categoría API3:2023 *Broken Object Property Level Authorization*, que fusiona "excessive data exposure" y "mass assignment" de la lista de 2019. Ejemplo típico: un cliente que cambia un campo que no debería poder escribir (rol, "verified", etc.). Mitigaciones: listas blancas explícitas de campos de entrada y de salida. — [Barracuda (resumen de OWASP API3:2023)](https://blog.barracuda.com/2023/05/23/owasp-top-10-api-broken-object-property-level-authorization); [OWASP API Security Project](https://owasp.org/projects/api-security-project). La redacción oficial solo se vio en vista previa; los detalles vienen de resúmenes secundarios.
- **Rate limiting (Auth).** Supabase Auth aplica un token bucket por IP con "maximum capacity of 30 requests", y responde "429 Too Many Requests" al superarlo. Los límites se pueden configurar en el panel o por la Management API (`rate_limit_anonymous_users`, etc.). — [Supabase: Rate limits](https://supabase.com/docs/guides/auth/rate-limits)
- **Protección contra bots en el registro anónimo.** Supabase dice que "bad actors can abuse the endpoint to increase your database size drastically" y que "It is strongly recommended to enable invisible CAPTCHA or Cloudflare Turnstile". El límite por IP para sign-ins anónimos es de 30 por hora. — [Supabase: Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous)
- **Sesiones y contraseñas.** Con Supabase Auth, "The user still signs in and gets their own JWT"; usar la clave publishable no cambia la autenticación del usuario. — [Supabase: Migrating to new API keys](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys). Con sign-in anónimo no se recogen email ni contraseña: "without requiring users to enter an email address, password... or provide any other PII". — [Supabase: Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous)
- **Validación solo en cliente = inútil contra trampas.** Hay un caso real en itch.io: un jugador llegó al #1 con un tiempo negativo llamando directamente a `submitScore()` desde la consola del navegador, porque el juego solo validaba en el cliente. — [itch.io (comentario)](https://itch.io/post/13110590), vía [resumen de búsqueda]; también [Bugnet: Debugging leaderboard anomalies](https://bugnet.io/blog/debugging-leaderboard-anomalies) ("Client-side score validation is not useful for anti-cheat purposes").

### Inferencias
- Mapeo de los puntos del checklist para SYNAPSE con un leaderboard sobre un BaaS:
  - *Claves de API:* la clave publishable (Supabase) o la configuración web de Firebase pueden ir en el APK/PWA. Ninguna clave privilegiada (secret, service_role, cuenta de servicio de Google) debe acabar en el bundle de Vite ni en el repositorio público. Si hay verificación en servidor, debe vivir en una Edge Function o Cloud Function.
  - *Clave pública de la BD + RLS:* son lo mismo visto desde dos lados. La clave es pública por diseño; la seguridad real está en la RLS o en las Rules.
  - *Autenticación:* sin identidad, "una entrada por usuario y día" no se puede aplicar. La opción mínima es el sign-in anónimo (Supabase/Firebase) o Play Games Services v2 en Android.
  - *Restringir el acceso a registros:* el usuario solo inserta su fila; todos leen la tabla pública del ranking, pero solo las columnas necesarias.
  - *Bloquear la manipulación de campos:* columnas como `verified`, `rank`, `created_at` o `user_id` no deben ser escribibles por el cliente.
  - *Cookies de sesión:* poco relevante. supabase-js y Firebase guardan los tokens en almacenamiento local o del WebView, no en cookies, y no hay un servidor propio que emita cookies. Si algún día hubiera un backend propio con cookies, aplicarían HttpOnly/Secure/SameSite. Esto es una inferencia; no se buscó fuente específica.
  - *Hashing de contraseñas:* no aplica si no se gestionan contraseñas propias. Lo delega Auth del proveedor, o se evita con sign-in anónimo o de Play Games.
  - *Rate limiting y protección contra bots:* sí aplican: en Auth (anónimo), en el endpoint de envío de puntuación y en las lecturas del ranking.
  - *Consultas parametrizadas:* PostgREST y Firestore no construyen SQL a partir de strings del cliente. El riesgo reaparece si se escriben funciones RPC/PLpgSQL con SQL dinámico (`EXECUTE`) o Edge Functions que concatenen SQL. Esto es una inferencia; no se encontró fuente específica de Supabase durante esta búsqueda.
  - *Validación de entrada:* en la BD (CHECK, tipos, longitudes) o en Rules, nunca solo en el cliente.
  - *Devolver solo los datos necesarios:* el ranking público debe exponer, por ejemplo, `nickname, score, fecha`, nunca `user_id`, identificadores de dispositivo ni metadatos de attestation.

### Lagunas
- No se pudo leer directamente la página oficial de OWASP API Top 10 2023 ni ASVS; las descripciones de API3 vienen de resúmenes secundarios.

## Pregunta 2: Opciones (Play Games Services v2 vs Firebase vs Supabase): estado en 2026, anti-tamper, soporte web/PWA y coste/complejidad para un desarrollador en solitario

### Conclusión
Play Games Services (PGS) v2 es lo más barato en esfuerzo de backend, porque Google aloja los leaderboards y ofrece límites de puntuación y "tamper protection". Pero esa protección es solo para Android, no hay un SDK web documentado para la PWA, y en Capacitor 8 haría falta un plugin nativo; el plugin comunitario más conocido solo declara soporte hasta Capacitor 5. Firebase (Firestore + Rules + App Check) y Supabase (Postgres + RLS + Edge Functions) sirven para Android y web por igual. Exigen escribir y probar las reglas uno mismo, y ninguno impide por sí solo las puntuaciones falsificadas.

### Hallazgos citados

**Play Games Services**
- El SDK v1 está obsoleto desde septiembre de 2025, con el siguiente calendario: "Google Play prevents publishing new titles that use the v1 SDK and APIs". La API v1 se eliminó del SDK el 15 de junio de 2026 (`play-services-games:25.0.0`). En mayo de 2027, "All traffic from Play Games Services v1 blocked". Además, "play-services-auth no longer provides GSI as of May 2026". La propia página es inconsistente: menciona "June 2027" en un resumen y "May 2027" en la tabla. — [Android Developers: PGS deprecation schedule](https://developer.android.com/games/pgs/deprecation)
- Leaderboards de PGS: hasta 70 por juego. El SDK "automatically creates daily, weekly, and all-time versions"; los diarios "reset at UTC-7". — [Android Developers: PGS Leaderboards](https://developer.android.com/games/pgs/leaderboards)
- Límites de puntuación: "optional values that define the lower and upper limits of scores... This can help you discard score submissions that are clearly fraudulent." — [PGS Leaderboards](https://developer.android.com/games/pgs/leaderboards)
- Tamper protection: "checks for suspected tampered scores and hides them automatically. This feature is available for Android games only". Viene activada por defecto en leaderboards nuevos y puede tardar hasta 24 h en surtir efecto. Google sugiere desactivarla si "your game also runs on the web in addition to Android, and shares leaderboards across these platforms". También existe `Players.hide` para ocultar a los tramposos de todos los leaderboards. — [PGS Leaderboards](https://developer.android.com/games/pgs/leaderboards)
- La página de leaderboards lista implementaciones cliente para Android, "Web (REST API)" y C++. La API REST está en `games.googleapis.com` e incluye los recursos leaderboards y scores. — [PGS Leaderboards](https://developer.android.com/games/pgs/leaderboards); [PGS REST reference](https://developer.android.com/games/services/web/api/rest)
- La página general de PGS describe la plataforma como "a unified gaming ecosystem encompassing Android, ChromeOS, and Windows PC" y no menciona web/navegador. Dice que v2 "automatically recognizes the player when the game starts". También indica que PGS "does not serve as a primary system for inventory management or game-state preservation". — [Android Developers: PGS overview](https://developer.android.com/games/pgs/overview)
- Plugin de Capacitor: `@openforge/capacitor-game-connect` ofrece Sign-In, Leaderboard y Achievements para Game Center y PGS. Su tabla de soporte solo lista "Capacitor v5 ✅ / v4 ✅ / v3 ✅"; no dice nada de v6–v8 ni de si usa PGS v1 o v2. — [GitHub openforge/capacitor-game-connect](https://github.com/openforge/capacitor-game-connect)

**Firebase (solo fragmentos; firebase.google.com no fue accesible)**
- App Check en web con reCAPTCHA Enterprise: según la guía web de Firebase, hasta 10.000 evaluaciones al mes sin coste y a partir de ahí de pago. Firebase recomienda reCAPTCHA Enterprise frente a v3 para integraciones nuevas. — [Firebase: App Check web (reCAPTCHA)](https://firebase.google.com/docs/app-check/web) (visto vía buscador). Un hilo de Reddit de 2024, fuente secundaria, cita un email de Google: 10.000 gratis/mes desde el 1 de abril de 2024 y 1 $ por cada 1.000 evaluaciones. — [r/Firebase](https://lr.ggtyler.dev/r/Firebase/comments/1ae5bh4/google_recaptcha_price_changes)
- Replay protection de App Check (limited-use tokens): el token "can be used only once", lo que añade latencia y a veces coste según el proveedor. Requiere Web SDK v12.14.0+ o Android BoM v34.14.0+ (App Check 19.1.0+). En web se usa `getLimitedUseToken()` (beta). Se puede activar en modo "monitoring" antes de "enforced". — [Firebase: Protect custom backend resources with App Check (web)](https://firebase.google.com/docs/app-check/web/custom-resource) (visto vía buscador)
- App Check "is subject to the quotas and limits of the attestation providers you use". — [Firebase: App Check overview](https://firebase.google.com/docs/app-check) (visto vía buscador)

**Play Integrity (lo usa App Check en Android)**
- Verdicts: `appIntegrity` (binario sin modificar reconocido por Play), `deviceIntegrity` (dispositivo certificado) y `accountDetails` (licencia), además de verdicts opcionales (`appAccessRiskVerdict`, `recentDeviceActivity`, `deviceRecall` beta). Cuota por defecto: "up to 10,000 total requests per day across all installs", ampliable bajo petición. Google la recomienda "alongside other signals... and not as your sole anti-abuse mechanism". Las standard requests tienen latencia de "a few hundred milliseconds" y mitigación automática de replay. — [Android Developers: Play Integrity overview](https://developer.android.com/google/play/integrity/overview) (actualizada el 2026-04-20)

**Supabase**
- Plan gratuito (según fuentes secundarias de 2026, no verificadas en la página de precios oficial): 2 proyectos activos, 500 MB de BD, 50.000 MAU, 500.000 invocaciones de Edge Functions al mes, y pausa automática tras 7 días de inactividad. — [JetAdmin: Supabase pricing 2026](https://www.jetadmin.io/blog/supabase-pricing-2026-guide-to-plans-limits-and-real-world-costs/); [automationatlas.io](https://automationatlas.io/answers/supabase-free-tier-limits-2026/). Una fuente de 2025 da cifras distintas (1.000 invocaciones/día), lo que supone un conflicto. — [UIBakery](https://uibakery.io/blog/supabase-pricing)
- Una fuente secundaria afirma que los proyectos nuevos creados después del 30 de mayo de 2026 necesitan GRANTs explícitos de Postgres para el acceso por PostgREST, y que los proyectos gratuitos existentes se verán afectados desde el 30 de octubre de 2026. — [JetAdmin](https://www.jetadmin.io/blog/supabase-pricing-2026-guide-to-plans-limits-and-real-world-costs/). Esto concuerda parcialmente con la doc oficial de RLS ("enable RLS yourself and grant only the permissions each Postgres role needs") — [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). La fecha exacta no está verificada.
- Supabase no ofrece una attestation equivalente a App Check; para frenar bots en Auth recomienda CAPTCHA/Turnstile. — [Supabase: Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous)

### Inferencias
- **PGS v2:** es la opción más proporcionada si el leaderboard es **solo Android**. Hosting, UI de ranking, reset diario, límites de puntuación, tamper protection y moderación de nombres (son los perfiles de Play Games) vienen incluidos, sin coste de backend documentado. Contras:
  1. La PWA se quedaría fuera, o habría que desactivar la tamper protection si se comparte con web.
  2. Hay que integrar un plugin nativo en Capacitor 8; no se encontró ninguno con soporte declarado para v8, así que probablemente toque escribir un plugin Capacitor propio en Kotlin.
  3. El reset diario de PGS es en UTC-7, mientras que la semilla Daily de SYNAPSE se deriva de "la fecha". Si esa fecha es local o UTC, la ventana del leaderboard diario no coincidirá con el día del puzzle.
  4. La tamper protection detecta clientes modificados, pero no un bot que juega con el APK legítimo.
- **Firebase:** la mejor attestation multiplataforma lista para usar (Play Integrity en Android, reCAPTCHA Enterprise en web), las Rules son declarativas y el free tier es generoso. Contras: el lenguaje de Rules es propio, y la verificación seria (re-simulación) requiere Cloud Functions, que necesitan el plan Blaze (de pago por uso) según el conocimiento general. Esto último no se verificó en esta búsqueda.
- **Supabase:** Postgres + RLS + CHECK constraints + funciones SQL resultan familiares, y las Edge Functions (Deno/TypeScript) podrían reutilizar el código TS del juego para re-simular. Contras: no hay attestation integrada (habría que verificar tokens de Play Integrity a mano en una Edge Function) y el proyecto gratuito se pausa por inactividad. Además, hay que vigilar dos cambios de 2026: el fin de las claves legacy a final de año y los GRANTs explícitos.
- Para un desarrollador en solitario, la complejidad sube así: PGS solo Android < Supabase/Firebase con validación por reglas < cualquiera de los dos con re-simulación en servidor + attestation.

### Lagunas
- No se encontró documentación oficial actual de un SDK web/JS de PGS v2 para juegos de navegador. La URL `developer.android.com/games/pgs/web` devuelve 404. No está claro si un juego web puede autenticar jugadores y enviar puntuaciones a PGS hoy.
- No se verificó si PGS tiene coste o cuotas de API relevantes para leaderboards.
- No se pudo leer la página oficial de precios de Firebase (Blaze vs Spark para Functions/App Check) ni la de Supabase.
- No se verificó si existe algún plugin Capacitor 7/8 mantenido para PGS v2.

## Pregunta 3: Anti-cheat para puntuaciones calculadas en el cliente: por qué se pueden falsificar, mitigaciones y qué hacen los juegos reales

### Conclusión
Cualquier puntuación enviada por un cliente que controla el usuario (PWA en un navegador con DevTools, APK que se puede descompilar) se puede falsificar: basta con llamar al endpoint con el token propio. Las defensas eficaces son:
- **Plausibilidad en el servidor:** límites de puntuación, duración mínima y máxima, una entrada por usuario y día.
- **Re-simulación en el servidor:** enviar las respuestas o inputs con tiempos y que el servidor recalcule la puntuación con la misma semilla.
- **Attestation** (Play Integrity / App Check), como capa de defensa adicional.
- **Moderación a posteriori:** ocultar a los tramposos.

Un caso específico de SYNAPSE: la semilla del Daily se deriva de la fecha, así que es pública y predecible. Un bot puede resolver los 7 puzzles al instante, y la re-simulación solo comprueba que los inputs y la puntuación sean coherentes, no que los haya producido un humano.

### Hallazgos citados
- "Client-side score validation is not useful for anti-cheat purposes. A cheating client can bypass any validation the client performs." La guía recomienda combinar validación en servidor, análisis de logs de sesión y detección estadística de outliers, con revisión humana para los casos dudosos ("inputs to a decision, not the decision itself"). — [Bugnet: Debugging Leaderboard Score Anomalies](https://bugnet.io/blog/debugging-leaderboard-anomalies)
- Patrón de re-simulación (propuesta en el juego *snail*, que cita crimson.land como precedente): el servidor carga el núcleo del juego como WASM, "replays every tick", rechaza la partida si no coinciden resultado, tiempo, kills y "final RNG state", y comprueba que cada input sea humanamente posible. — [GitHub banteg/snail issue #27](https://github.com/banteg/snail/issues/27)
- El mismo issue identifica el "seed shopping": si el cliente elige la semilla, puede probar semillas offline. Con semilla fija para todos el problema desaparece. — [GitHub banteg/snail issue #27](https://github.com/banteg/snail/issues/27)
- Otro proyecto describe el arreglo provisional (scores desde el navegador; los tramposos determinados se ocultan manualmente) y propone la re-simulación desde semilla + inputs como solución definitiva. — [GitHub TylerBielman/gametronyx issue #27](https://github.com/TylerBielman/gametronyx/issues/27)
- Flujo similar descrito por un desarrollador: el cliente envía la semilla y un array comprimido de acciones con timestamps, y el backend re-simula y compara contra límites. Es un artículo de blog (DEV), de menor autoridad. — [DEV Community](https://dev.to/krrish-ranjan/if-your-game-client-sends-raw-scores-youre-already-hacked-building-a-real-time-web3-arcade-engine-2h8i)
- PGS: límites mínimo y máximo de puntuación, tamper protection automática (solo Android), y `Players.hide` para ocultar jugadores fraudulentos. — [PGS Leaderboards](https://developer.android.com/games/pgs/leaderboards)
- Play Integrity está pensado para "combat cheating", pero "works best when used alongside other signals... not as your sole anti-abuse mechanism". Desaconseja cachear verdicts porque eso "increases the risk of proxying". `recentDeviceActivity` detecta volúmenes anómalos de peticiones por dispositivo. — [Play Integrity overview](https://developer.android.com/google/play/integrity/overview)
- Anti-replay: los tokens limited-use de App Check son de un solo uso. — [Firebase App Check custom resource (web)](https://firebase.google.com/docs/app-check/web/custom-resource) (vía buscador). En Play Integrity, `requestHash`/`nonce` ligan el token a la petición concreta, y Google advierte que esos datos son visibles en claro: "You should encrypt or hash the data before passing it". — [Play Integrity overview](https://developer.android.com/google/play/integrity/overview)
- Algunos backends de leaderboards alojados anuncian comprobaciones en servidor, como la duración real de la sesión o topes por juego. Es una afirmación del vendedor, no verificada. — [CheddaBoards](https://cheddaboards.com/)

### Inferencias
- **Por qué cualquier envío es falsificable en SYNAPSE:** la puntuación sale de código JS que el usuario puede leer y modificar, y el token de sesión (anónimo o no) está en el dispositivo. Firmar las peticiones con una clave embebida en el APK o en la PWA no sirve, porque la clave se extrae. Solo la attestation de plataforma (Play Integrity) aporta una firma que el cliente no puede falsificar fácilmente, y aun así no detecta a un humano que juega con un bot externo o con un dispositivo auxiliar.
- **Escalera proporcionada para el Daily de SYNAPSE**, de menor a mayor coste:
  1. **Identidad mínima + una entrada por usuario y día:** clave única `(user_id, daily_date)`, solo INSERT, sin UPDATE ni DELETE. Elimina el reintento de partidas.
  2. **Plausibilidad en la BD o en la función:** `score` entre 0 y el máximo teórico del Daily (que se puede calcular, porque los 7 puzzles y la escala de puntos son deterministas), duración total ≥ un mínimo humano por puzzle, `daily_date` = fecha del servidor (±1 día por zonas horarias) y `created_at` puesto por el servidor.
  3. **Re-simulación:** el cliente envía `{daily_date, respuestas[], tiempos_ms[]}` en lugar de `score`. Una Edge Function o Cloud Function regenera los 7 puzzles con la misma semilla (reutilizando el módulo TS del generador y del puntuador) y calcula la puntuación. Como el Daily ya es determinista por fecha, es la mitigación más natural. El coste es que el núcleo de puntuación debe ser puro y determinista; los sistemas de multiplicador y "heat" dependen de tiempos que el cliente declara.
  4. **Attestation:** Play Integrity (Android) o App Check (Android + web). Sube el coste de automatizar, pero no lo impide.
  5. **Moderación a posteriori:** campo `hidden` solo escribible por el admin y detección de outliers (tiempos imposiblemente consistentes, puntuación perfecta a los pocos segundos de publicarse el Daily).
- **Límite propio del Daily:** como la semilla es pública (derivada de la fecha), quien lea el código puede pre-generar y resolver los puzzles. La re-simulación no detecta eso si los tiempos declarados parecen humanos. Las opciones son: a) aceptar este riesgo residual (es lo habitual en juegos casuales); b) que el servidor entregue la semilla o los puzzles del día al empezar y registre la hora de inicio, para medir la duración en el servidor; c) mostrar rankings por amigos o percentiles en lugar de un top global, lo que reduce el incentivo. Pasar a una semilla emitida por el servidor rompe el diseño 100 % offline del Daily.
- **Contexto del proyecto:** la lista de tareas de SYNAPSE incluye haber cerrado "the pause/background mulligan exploit". Con un leaderboard, cualquier exploit de este tipo que quede en el cliente pasaría a afectar a la clasificación global.

### Lagunas
- No se encontraron postmortems formales de juegos web o móviles comerciales sobre trampas en leaderboards (por ejemplo, Wordle/NYT Games, Duolingo, Lumosity o Elevate). Las fuentes encontradas son issues de GitHub, blogs y comentarios de itch.io.
- No se encontró documentación sobre la eficacia medida de la tamper protection de PGS.

## Pregunta 4: Qué debe imponer una configuración de Supabase o Firebase

### Conclusión
Supabase: RLS activada; una política INSERT con `with check (auth.uid() = user_id)`; ninguna política UPDATE ni DELETE para clientes; GRANTs mínimos o privilegios por columna, de forma que el cliente no pueda escribir `verified`, `rank` ni `created_at`; CHECK constraints o un trigger para los rangos; una vista o RPC pública que devuelva solo las columnas necesarias (con `security_invoker`); y las secret keys solo en Edge Functions. La alternativa más robusta es revocar el INSERT directo y obligar a enviar la puntuación por una Edge Function o RPC que valide o re-simule y escriba con privilegios. Firebase: Rules con `request.auth.uid` como propietario, `keys().hasOnly()` en create, ningún update/delete, validación de tipo y rango, y App Check en modo enforced.

### Hallazgos citados
- **INSERT solo de la fila propia (Supabase):** "You can specify insert policies with the `with check` clause... ensures that any new row data adheres to the policy constraints". El ejemplo de la doc comprueba que el ID de usuario coincide con el valor insertado, con `to authenticated`. — [Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **Sin política = sin acceso:** RLS funciona como "adding a WHERE clause to every query"; los roles `anon`/`authenticated` solo pueden hacer lo que permitan las políticas y los GRANTs. — [Supabase: Column Level Security](https://supabase.com/docs/guides/database/postgres/column-level-security); [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **Restricción por columna:** la RLS "doesn't give you control over which columns they can access within rows". Para eso se usan privilegios de columna: `revoke update on table ... from authenticated; grant update (title, content) on table ... to authenticated;`. Advertencias: es "an advanced feature" ("We do not recommend using column-level privileges for most users"); los roles restringidos no pueden usar `select *`; y si existe un privilegio a nivel de tabla, revocar el de columna no tiene efecto. — [Supabase: Column Level Security](https://supabase.com/docs/guides/database/postgres/column-level-security)
- **Usuarios anónimos frente a permanentes:** los usuarios anónimos usan el rol `authenticated`, y el JWT incluye `is_anonymous`, que se puede usar en políticas restrictivas. Por ejemplo, solo usuarios permanentes podrían publicar. — [Supabase: Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous)
- **Bypass:** las secret/service keys se saltan la RLS y "should never be used in the browser or exposed to customers". También existen roles con `bypassrls`. — [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security); [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)
- **Vistas:** usar `with (security_invoker = true)`, o revocar el acceso o mover la vista a un esquema no expuesto. — [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **Security Advisor:** Supabase revisa constantemente los problemas comunes con los roles integrados. — [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys); [Production Checklist](https://supabase.com/docs/guides/deployment/going-into-prod)
- **Firestore, restricción de campos:** en create, "list only the fields that are explicitly allowed... then use hasOnly()" (combinado con `hasAll` para los obligatorios). En update, `keys()` representa el documento completo tras el cambio, así que hay que usar `request.resource.data.diff(resource.data).affectedKeys()` para ver qué campos cambian. — [Firebase: Control access to specific fields](https://firebase.google.com/docs/firestore/security/rules-fields) (vía buscador); [Firebase blog: new Firestore rules features (2020)](https://firebase.blog/posts/2020/06/new-firestore-security-rules-features)
- **Firestore, propiedad:** las restricciones de campo no limitan quién escribe si falta la comprobación de propietario (`resource.data.uid == request.auth.uid`). — fuente secundaria: [Firebase security rules auditor skill](https://mcpservers.org/vi/agent-skills/firebase/firebase-security-rules-auditor)

### Inferencias
Esquema mínimo sugerido para Supabase (es una inferencia de diseño; no se probó contra una BD real):
- Tabla `daily_scores(id, user_id uuid default auth.uid(), daily_date date, score int, duration_ms int, nickname text, verified bool default false, hidden bool default false, created_at timestamptz default now())`, con `unique(user_id, daily_date)` y `CHECK (score between 0 and <máx teórico>)`, `CHECK (duration_ms between <mín> and <máx>)` y `CHECK (char_length(nickname) between 3 and 20)`.
- RLS activada. Política INSERT `to authenticated with check (user_id = (select auth.uid()) and daily_date between current_date - 1 and current_date + 1)`. Ninguna política UPDATE ni DELETE.
- `revoke insert, update, delete on daily_scores from anon, authenticated` y luego `grant insert (daily_date, score, duration_ms, nickname) to authenticated`. Así `verified`, `hidden`, `created_at` y `user_id` toman sus valores por defecto o los escribe el servidor.
- Lectura pública mediante una vista `security_invoker` o una función RPC `get_daily_leaderboard(date)` que devuelva solo `nickname, score` y la posición calculada (nunca `user_id`), paginada o limitada al top N.
- Variante más robusta: revocar todo el INSERT del cliente; el cliente llama a una Edge Function `submit-daily` que verifica el JWT y (opcionalmente) el token de Play Integrity, re-simula y escribe con la secret key.
- Firebase equivalente: `match /daily/{date}/scores/{uid}` con `allow create: if request.auth.uid == uid && request.resource.data.keys().hasOnly(['score','durationMs','nickname']) && request.resource.data.score is int && request.resource.data.score >= 0 && request.resource.data.score <= MAX;`, `allow update, delete: if false;`, y App Check en enforced. El ID del documento igual al `uid` garantiza una entrada por usuario y día.

### Lagunas
- No se verificó en la doc oficial de Firestore el texto exacto de las funciones de Rules (`is int`, límites de longitud de strings); se citan a partir de fragmentos de buscador y del blog de Firebase.
- No se verificó la fecha exacta del cambio de GRANTs explícitos en Supabase (30 de mayo / 30 de octubre de 2026) en una fuente primaria.

## Pregunta 5: Privacidad y Google Play: nicknames (UGC), Data safety, borrado de cuenta y Familias

### Conclusión
Un leaderboard con nicknames libres es contenido generado por usuarios (UGC) según la política de Play. Exige aceptar unos términos antes de crear contenido, moderación continua y mecanismos accesibles en la app para reportar y bloquear. Si se crean cuentas, también hace falta borrado de cuenta dentro de la app más un enlace web, declarado en Data safety. El formulario de Data safety también tiene que reflejar los nuevos datos recogidos y compartidos. Si SYNAPSE apunta a niños, el UGC abierto choca con la política de Familias. Usar PGS (nombres de perfil de Play Games) o nicknames generados o elegidos de una lista reduce mucho esta carga.

### Hallazgos citados
- La política de UGC de Play define el UGC como contenido aportado por usuarios y visible para al menos parte de los demás usuarios, e incluye expresamente "user profiles, usernames". Exige: aceptar términos o una política de usuario antes de crear UGC; definir y prohibir el contenido objetable; moderación "robust, effective, and ongoing"; y un sistema in-app para reportar y bloquear contenido y usuarios, fácil de encontrar. — [Google Play: User Generated Content policy](https://support.google.com/googleplay/android-developer/answer/9876937) (vía buscador)
- La política de UGC indica que los niños, según la definición de la política de Familias, deben quedar explícitamente excluidos mediante filtrado de edad en ciertos tipos de apps de UGC. Esto choca con un público infantil. — [Google Play: UGC policy](https://support.google.com/googleplay/android-developer/answer/9876937) (vía buscador)
- Borrado de cuenta: si la app permite crear cuentas, debe ofrecer una vía in-app para borrar la cuenta y sus datos, más un enlace web. La desactivación o congelación no cuenta como borrado. La retención por seguridad o fraude debe divulgarse. Todo esto se declara en el formulario de Data safety. — [Google Play: Understanding app account deletion requirements](https://support.google.com/googleplay/android-developer/answer/13327111) (vía buscador)
- Familias: las apps sociales infantiles o con funciones sociales deben ofrecer recordatorios de seguridad, aprobación de un adulto antes de activar chat que permita compartir información personal, y gestión continua de las funciones sociales. Según el resumen de búsqueda, a partir del 26 de agosto de 2026 se prohíben las apps de chat anónimo dirigidas a niños. — [Google Play: Families policies](https://support.google.com/googleplay/android-developer/answer/9893335); [Policy updates](https://support.google.com/googleplay/android-developer/answer/14554575) (vía buscador)
- Para el sign-in anónimo de Supabase no hay limpieza automática; los usuarios anónimos hay que borrarlos con SQL (por ejemplo, los de más de 30 días). — [Supabase: Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous)
- PGS muestra nombres de jugador que "may contain Unicode characters", y la UI propia debe manejarlos. — [PGS Leaderboards](https://developer.android.com/games/pgs/leaderboards)

### Inferencias
- **Nicknames:**
  - Opción menos costosa: no permitir texto libre (generar "Neurona-4821" o combinaciones de listas de palabras) o usar el nombre de Play Games (PGS).
  - Si se permite texto libre: limitar la longitud y el conjunto de caracteres, normalizar Unicode (evitar homoglifos, caracteres de control y RTL override), filtrar con una lista de palabras prohibidas en la BD o la función, renderizar siempre con `textContent` (nunca `innerHTML`, por XSS), añadir botones de reportar y ocultar y un campo `hidden` gestionado por el admin, y redactar unos términos de uso.
  - El riesgo de XSS es real porque SYNAPSE corre en un WebView de Capacitor y en una PWA: un nickname inyectado se ejecutaría en el contexto de la app.
- **Data safety:** con un leaderboard pasan a recogerse y compartirse con un tercero (Supabase/Google) un identificador de usuario o dispositivo, el nickname y los datos de la actividad de juego (la puntuación). Habría que actualizar el formulario y la política de privacidad, que hoy probablemente declaran "no se recogen datos". Si se usa Play Integrity o App Check, conviene revisar si implica declarar identificadores de dispositivo. Esto no se verificó.
- **Borrado de cuenta:** el sign-in anónimo crea una cuenta en sentido técnico. Es prudente ofrecer en la app un "Borrar mis datos del ranking" (DELETE vía RPC o Edge Function) y un enlace web, aunque no haya email ni contraseña. Que las cuentas anónimas cuenten como "cuentas" para Play no se verificó.
- **Familias:** un juego de entrenamiento cognitivo puede atraer a menores. Si en Play Console se declara público infantil, un leaderboard con nicknames libres es arriesgado; un ranking sin texto libre (alias generados) o solo de percentiles minimiza el problema.

### Lagunas
- No se pudo leer el texto completo de la política de UGC, la de Familias ni la de borrado de cuenta (solo fragmentos de buscador).
- No se encontró guía de Google específica sobre si un leaderboard con alias generados (no editables) se considera UGC.
- No se verificó qué debe declararse en Data safety cuando se usan Play Integrity o App Check.
